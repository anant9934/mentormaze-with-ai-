# MentorMaze --- Database Schema & Entity Relationship Design (ERD)

**Product:** MentorMaze\
**Phase:** Phase 1 --- Human Mentorship + Human Mock Interviews\
**Database:** PostgreSQL\
**ORM baseline:** Drizzle ORM\
**Parent ecosystem:** AI Tathastu\
**Document type:** Logical data model + implementation specification\
**Status:** Engineering baseline; validate open product decisions before
production migrations

------------------------------------------------------------------------

# 1. Purpose and Scope

This document translates the MentorMaze Phase 1 PRD into a relational
data architecture.

The database must support:

-   Independent and AI Tathastu authentication.
-   Role-based access control.
-   Student and mentor profiles.
-   Mentor applications and admin verification.
-   Consent-based context exchange with AI Tathastu and other approved
    ecosystem systems.
-   Evidence-backed skills and career goals.
-   Explainable mentor recommendations.
-   Availability, booking, rescheduling and cancellation.
-   LiveKit session metadata and participant authorization.
-   Student--mentor conversations and notifications.
-   Human mock interviews and rubric-based feedback.
-   Mentorship action items, milestones and progress.
-   Admin operations, support and audit history.

AI mentorship is not a Phase 1 feature. The schema should preserve
extensibility for Phase 2 without introducing unnecessary AI-agent
tables now.

## 1.1 Design principles

1.  PostgreSQL is the source of truth for MentorMaze transactional data.
2.  External systems remain authoritative for their own records.
3.  Authentication is separate from data-sharing consent.
4.  Every imported fact retains source and freshness metadata.
5.  Private notes, student-visible summaries and admin-only notes are
    distinct records or visibility classes.
6.  Booking correctness is enforced with transactions and database
    constraints---not only frontend checks.
7.  Important state transitions are auditable.
8.  Use normalized relational tables for core data; use JSONB only for
    genuinely variable provider payloads or versioned snapshots.
9.  Store files in private object storage, not as database blobs.
10. Do not create microservice-specific databases before the operational
    need exists.

# 2. Database Conventions

## 2.1 Naming

-   Tables: plural `snake_case`.
-   Columns: singular `snake_case`.
-   Primary keys: `id`.
-   Foreign keys: `<referenced_entity>_id`.
-   Timestamps: `created_at`, `updated_at`.
-   Soft deletion: `deleted_at` only where recovery or retention policy
    requires it.
-   Boolean fields: `is_...` or `has_...`.
-   Status values: explicit PostgreSQL enums or constrained text values.

## 2.2 Identifier strategy

Recommended: - UUID primary keys generated by the application or
PostgreSQL. - Never use email address as a primary key. - External
identity keys must use `(issuer, subject)` rather than email. - Public
profile slugs may be separate, non-sensitive identifiers.

## 2.3 Timestamp strategy

-   Store timestamps as `timestamptz` in UTC.
-   Store IANA timezone names such as `Asia/Kolkata` for user display
    preferences.
-   Use `date` for calendar-only values.
-   Use `time` for recurring weekly availability windows, interpreted in
    the mentor's timezone.
-   Preserve the timezone and original local selection for booking
    audit/debugging where useful.

## 2.4 Standard columns

Most mutable business tables should include:

``` sql
id uuid primary key default gen_random_uuid(),
created_at timestamptz not null default now(),
updated_at timestamptz not null default now()
```

Add `created_by`, `updated_by`, `deleted_at`, or `version` only where
required. Do not mechanically add meaningless columns to every table.

# 4. Identity, Authentication and Access Control

## 4.1 `users`

One canonical MentorMaze account per person.

  -----------------------------------------------------------------------
  Column                  Type                    Rules
  ----------------------- ----------------------- -----------------------
  `id`                    uuid                    PK

  `email`                 citext                  Nullable if provider
                                                  does not supply email;
                                                  unique when present

  `email_verified_at`     timestamptz             Nullable

  `phone_e164`            varchar(20)             Nullable

  `phone_verified_at`     timestamptz             Nullable

  `display_name`          varchar(160)            Required

  `avatar_file_id`        uuid                    Nullable FK to stored
                                                  files

  `account_status`        user_account_status     Active, pending,
                                                  suspended, closed

  `preferred_locale`      varchar(20)             Default `en`

  `timezone`              varchar(64)             IANA timezone

  `last_login_at`         timestamptz             Nullable

  `created_at`            timestamptz             Required

  `updated_at`            timestamptz             Required
  -----------------------------------------------------------------------

Indexes: - Unique normalized email where not null. - Index on
`account_status`. - Index on `created_at`.

Do not store passwords here if authentication is delegated to an OIDC
provider. If local email/password auth is implemented, credentials
should be held in a dedicated auth credential table with secure password
hashing and rotation policy.

## 4.2 `user_identities`

Links one user to one or more authentication identities.

  -------------------------------------------------------------------------
  Column                    Type                    Rules
  ------------------------- ----------------------- -----------------------
  `id`                      uuid                    PK

  `user_id`                 uuid                    FK users

  `issuer`                  text                    Provider issuer URL /
                                                    stable provider ID

  `subject`                 text                    Provider subject

  `provider`                varchar(40)             `ai_tathastu`,
                                                    `google`, `github`,
                                                    `email`, etc.

  `provider_email`          citext                  Nullable; informational
                                                    only

  `linked_at`               timestamptz             Required

  `last_authenticated_at`   timestamptz             Nullable
  -------------------------------------------------------------------------

Constraints: - Unique `(issuer, subject)`. - Index `user_id`. - Never
link accounts solely because two providers return the same email without
a verified linking flow.

## 4.3 `roles`

Seeded role definitions.

Suggested records: - `student` - `mentor` - `super_admin` -
`mentor_verification_admin` - `operations_admin` - `content_admin` -
`support_admin`

Columns: `id`, `key` unique, `name`, `description`, `is_system`,
timestamps.

## 4.4 `permissions`

Seeded permission catalog.

Examples: - `mentor.application.review` - `mentor.application.approve` -
`mentor.profile.manage` - `booking.manage` - `support.case.manage` -
`audit.read` - `integration.manage` - `user.suspend`

Columns: `id`, `key` unique, `description`.

## 4.5 `role_permissions`

Many-to-many relationship between roles and permissions.

Columns: - `role_id` FK roles. - `permission_id` FK permissions. -
Composite primary key `(role_id, permission_id)`.

## 4.6 `user_role_assignments`

Columns: - `id` - `user_id` - `role_id` - `assigned_by` FK users
nullable for system assignment. - `assigned_at` - `revoked_at` -
`revoked_by` FK users nullable.

Constraint: - At most one active assignment for a given
`(user_id, role_id)`.

A user can be both a student and an approved mentor. Admin roles must be
granted explicitly.

# 6. Mentor Applications and Verification

## 6.1 `mentor_applications`

Keep application history separate from the live public profile.

  Column                   Type                        Rules
  ------------------------ --------------------------- -----------------------
  `id`                     uuid                        PK
  `mentor_user_id`         uuid                        FK mentor_profiles
  `application_number`     varchar(32)                 Unique, non-sensitive
  `status`                 mentor_application_status   Required
  `submitted_at`           timestamptz                 Nullable
  `review_started_at`      timestamptz                 Nullable
  `reviewed_by`            uuid                        FK users nullable
  `reviewed_at`            timestamptz                 Nullable
  `decision_reason_code`   varchar(80)                 Nullable
  `applicant_message`      text                        Nullable
  `created_at`             timestamptz                 Required
  `updated_at`             timestamptz                 Required

Application states: - `draft` - `submitted` - `under_review` -
`more_information_required` - `approved` - `rejected` - `withdrawn`

Use a separate suspension state on the mentor profile or a status event;
do not rewrite an approved application as rejected when a mentor is
later suspended.

## 6.2 `mentor_evidence`

Metadata for private object-storage files and external references.

Columns: - `id` - `mentor_application_id` FK mentor_applications -
`evidence_type` controlled text: identity, education, employment,
certification, portfolio, other - `file_object_key` nullable -
`external_url` nullable - `original_filename` nullable - `mime_type`
nullable - `file_size_bytes` nullable - `uploaded_by` FK users -
`visibility` default `admin_only` - `created_at`

Store no public object URL. Use short-lived signed URLs after
authorization.

## 6.3 `mentor_verification_checks`

One row per check.

Columns: - `id` - `mentor_application_id` FK - `check_type` - `status`:
pending, passed, failed, waived, needs_more_information - `reviewer_id`
FK users - `review_notes` restricted admin-only - `evidence_id` FK
mentor_evidence nullable - `checked_at` - `created_at`

## 6.4 `mentor_application_events`

Append-only state history: - `id` - `application_id` - `from_status` -
`to_status` - `actor_user_id` - `reason_code` - `public_message`
nullable - `internal_note` nullable - `created_at`

Keep internal notes inaccessible to applicants and mentors.

# 7. Skills, Topics and Evidence

## 7.1 `skill_categories`

Columns: `id`, `name`, `slug`, `parent_id` nullable self-FK,
`description`.

## 7.2 `skills`

Columns: - `id` - `category_id` FK skill_categories - `name` - `slug`
unique - `description` - `is_active`

Canonicalize aliases separately if required.

## 7.3 `skill_aliases`

Columns: `id`, `skill_id`, `alias`, `normalized_alias`.

Unique normalized alias where appropriate.

## 7.4 `topics`

Topics are broader service areas, e.g. career guidance, resume review,
backend engineering, system design, behavioral interviews.

Columns: `id`, `name`, `slug` unique, `category`, `description`,
`is_active`.

## 7.5 `student_skills`

Columns: - `id` - `student_user_id` FK users - `skill_id` FK skills -
`self_assessed_level` nullable smallint 1--5 - `assessment_status`:
self_reported, evidence_supported, mentor_observed, assessed -
`last_demonstrated_at` nullable - `created_at` - `updated_at`

Unique `(student_user_id, skill_id)`.

Do not treat `self_assessed_level` as verified proficiency.

## 7.6 `mentor_expertise`

Columns: - `id` - `mentor_user_id` FK mentor_profiles - `skill_id` FK
skills nullable - `topic_id` FK topics nullable - `claimed_level`
nullable smallint 1--5 - `evidence_status`: claimed, evidence_reviewed,
verified_scope - `created_at`

Require at least one of `skill_id` or `topic_id`. Add unique constraints
to avoid duplicates.

## 7.7 `skill_evidence`

Generic evidence linking a user to a skill claim.

Columns: - `id` - `user_id` FK users - `skill_id` FK skills -
`evidence_type`: project, resume, certificate, assessment,
mentor_observation, course, other - `evidence_reference_id` nullable -
`description` - `source_fact_id` nullable FK profile_facts -
`review_status` - `reviewed_by` FK users nullable - `observed_at` -
timestamps

Evidence does not automatically prove mastery; retain evidence type and
review status.

## 8.3 `goal_milestones`

Columns: - `id` - `goal_id` FK student_goals - `title` - `description` -

Columns: - `id` - `student_user_id` FK users - `goal_id` FK

mentorship_sessions nullable - `title` - `description` -
`created_by_user_id` FK users - `assigned_to_user_id` FK users -

# 9. Consent, External Integrations and Context Provenance

## 9.1 `integration_providers`

Seeded provider registry: - AI Tathastu - Collabry - Avsar - IRIS -
Google / GitHub where used for identity or profile links

Columns: - `id` - `key` unique - `display_name` - `provider_type` -
`is_enabled` - `created_at`

A provider being registered does not imply that its data is available or
authorized.

## 9.2 `external_connections`

Columns: - `id` - `user_id` FK users - `provider_id` FK
integration_providers - `external_subject` nullable -
`connection_status`: active, expired, revoked, error - `connected_at` -
`last_successful_sync_at` nullable - `revoked_at` nullable - `metadata`
JSONB limited to non-secret metadata

Unique `(user_id, provider_id)` unless multiple connections are
explicitly supported.

Never store long-lived plaintext OAuth secrets in this table. Use
encrypted secret storage or a managed secrets service.

## 9.3 `consent_grants`

Columns: - `id` - `user_id` FK users - `provider_id` FK
integration_providers nullable - `purpose` e.g. profile_import,
mentor_context_sharing, outcome_export - `scope_key` -
`consent_version` - `status`: granted, revoked, expired - `granted_at` -
`revoked_at` nullable - `expires_at` nullable - `capture_method` -
`created_at`

A consent grant must be specific enough to answer what data may be used,
by which system, for what purpose, and when.

## 9.4 `consent_events`

Append-only consent history: - `id` - `consent_grant_id` - `event_type`:
granted, renewed, revoked, expired - `actor_user_id` -
`consent_version` - `event_payload` JSONB with non-sensitive audit
details - `created_at`

## 9.5 `profile_facts`

Normalized, provenance-aware facts imported or captured for a user.

Columns: - `id` - `user_id` FK users - `fact_type` e.g. education,
project, experience, achievement, career_interest - `fact_key` -
`value_json` JSONB - `visibility` private, selected_mentors, public -
`verification_status` unverified, source_confirmed, reviewed,
verified_scope - `observed_at` - `expires_at` nullable - `created_at` -
`updated_at`

Use structured domain tables for frequently queried facts. Use
`profile_facts` for extensible context, not as a replacement for all
relational modeling.

## 9.6 `profile_fact_sources`

Columns: - `id` - `profile_fact_id` FK profile_facts - `provider_id` FK
integration_providers nullable - `external_record_id` nullable -
`source_type`: user_input, ai_tathastu, resume, project, admin, other -
`source_updated_at` nullable - `imported_at` - `source_metadata` JSONB

This allows one fact to have multiple supporting or conflicting sources.

## 9.7 `external_sync_jobs`

Columns: - `id` - `connection_id` FK external_connections - `direction`:
inbound, outbound - `scope_key` - `status`: queued, running, succeeded,
partial, failed, cancelled - `idempotency_key` unique -
`attempt_count` - `started_at` - `completed_at` - `last_error_code`
nullable - `last_error_message_safe` nullable - `created_at`

Do not store access tokens or full sensitive payloads in job logs.

## 9.8 `external_sync_events`

Append-only record of each synchronization result: - `id` -
`sync_job_id` - `event_type` - `external_record_id` -
`local_record_type` - `local_record_id` - `result_status` -
`occurred_at`

## 9.9 Source-of-truth policy

Create a documented field ownership matrix before enabling bidirectional
sync.

Example: - MentorMaze owns booking status and MentorMaze session
records. - AI Tathastu owns its account identity and upstream academic
records. - Student owns their self-entered career goals unless they
explicitly choose a different workflow. - MentorMaze owns its
verification decisions. - A generated inference never silently
overwrites a verified source value.

`algorithm_version` - `feature_version` - `requested_filters` JSONB -
`candidate_count` - `result_count` - `status` - `created_at` -
`completed_at`

## 10.2 `matching_candidates`

One record per mentor considered in a run.

Columns: - `id` - `matching_run_id` FK matching_runs - `mentor_user_id`

JSONB - `shown_to_student_at` nullable - `created_at`

## 10.3 `matching_feedback`

Columns: - `id` - `matching_candidate_id` FK matching_candidates -

nullable - `created_at`

Do not interpret a profile view as proof of recommendation quality.

# 11. Availability, Booking and Scheduling

## 11.1 `availability_rules`

Recurring weekly mentor availability.

Columns: - `id` - `mentor_user_id` FK mentor_profiles - `weekday`
smallint 0--6 - `start_local_time` time - `end_local_time` time -
`timezone` varchar(64) - `valid_from` date nullable - `valid_until` date
nullable - `is_active` - timestamps

Constraint: `start_local_time < end_local_time`. For overnight
availability, represent as two windows or define explicit handling.

## 11.2 `availability_exceptions`

One-off overrides: - `id` - `mentor_user_id` - `starts_at` timestamptz -
`ends_at` timestamptz - `exception_type`: unavailable, available,
capacity_override - `reason` nullable - `created_at`

## 11.3 `bookings`

Core booking record.

  Column                          Type             Rules
  ------------------------------- ---------------- -----------------------------
  `id`                            uuid             PK
  `booking_reference`             varchar(32)      Unique
  `student_user_id`               uuid             FK users
  `mentor_user_id`                uuid             FK mentor_profiles
  `service_type`                  service_type     Mentorship / mock interview
  `service_topic_id`              uuid             FK topics nullable
  `status`                        booking_status   Required
  `starts_at`                     timestamptz      Required
  `ends_at`                       timestamptz      Required
  `timezone_at_booking`           varchar(64)      Required
  `student_timezone`              varchar(64)      Required
  `mentor_timezone`               varchar(64)      Required
  `student_context_note`          text             Nullable
  `cancellation_policy_version`   varchar(40)      Required
  `cancelled_by`                  uuid             FK users nullable
  `cancellation_reason_code`      varchar(80)      Nullable
  `cancelled_at`                  timestamptz      Nullable
  `confirmed_at`                  timestamptz      Nullable
  `created_at`                    timestamptz      Required
  `updated_at`                    timestamptz      Required

Constraints: - `ends_at > starts_at`. - Student and mentor must be
different users. - Index `(student_user_id, starts_at)`. - Index
`(mentor_user_id, starts_at)`. - Index `(status, starts_at)`.

Double-booking prevention: - Use a transaction that locks the mentor's
relevant schedule rows or a dedicated slot allocation record. - For
fixed-duration slots, consider a `booking_slots` table with a unique
mentor/time key. - For arbitrary intervals, use PostgreSQL range types
and an exclusion constraint where the product's concurrency model
supports it. - A frontend availability check alone is insufficient.

## 11.4 `booking_events`

`to_status` - `actor_user_id` nullable - `reason_code` - `metadata`
JSONB - `created_at`

## 11.5 `booking_holds`

## 11.6 Booking status values

# 20. Booking Concurrency and Transaction Design

Booking is one of the highest-risk data workflows.

A safe confirmation operation should:

1.  Authenticate the student.
2.  Authorize access to the requested service.
3.  Verify mentor is approved and accepting the service.
4.  Begin a database transaction.
5.  Recompute availability for the requested interval.
6.  Lock the relevant slot or schedule allocation.
7.  Check no conflicting confirmed booking or active hold exists.
8.  Create booking and event records.
9.  Create associated session metadata.
10. Commit.
11. Publish notification events through an outbox after commit.

For payment-enabled bookings, use a payment intent and explicit state
machine. Never mark a booking paid based only on a browser redirect.

## 20.1 Outbox pattern

For reliable notifications and integration events, add:

`outbox_events` - `id` - `aggregate_type` - `aggregate_id` -
`event_type` - `payload` - `occurred_at` - `published_at` -
`attempt_count` - `last_error_code`

Insert the outbox row in the same transaction as the business change. A
worker publishes it and marks it delivered. Consumers should be
idempotent.

# 21. Data Retention, Deletion and Privacy

Create a retention matrix before launch.

  -----------------------------------------------------------------------
  Data                                Suggested policy decision
  ----------------------------------- -----------------------------------
  Account identity                    Retain while account is active;
                                      define closure process

  External connection tokens          Revoke and delete according to
                                      provider/security policy

  Consent history                     Retain necessary evidence of
                                      consent and revocation

  Imported context                    Delete or de-identify according to
                                      purpose and revocation policy

  Mentor evidence                     Retain only for verification and
                                      legal/policy needs

  Bookings                            Retain according to
                                      operational/legal requirements

  Messages                            Define retention and user deletion
                                      behavior

  Session notes                       Define separate retention for
                                      private and shared notes

  Mock interview reports              Retain for user value and stated
                                      purpose

  Audit logs                          Retain under security and legal
                                      policy

  Uploaded files                      Apply expiry, deletion, and access
                                      review
  -----------------------------------------------------------------------

Deletion should be a workflow: 1. Verify requester. 2. Identify affected
records and legal retention exceptions. 3. Revoke external tokens. 4.
Stop scheduled sync jobs. 5. Delete or anonymize eligible records. 6.
Preserve legally required audit records without unnecessary personal
content. 7. Propagate eligible deletion requests to connected systems.
8. Record completion and exceptions.

Do not promise that revoking a connection automatically deletes all
previously imported data unless that behavior is implemented and
documented.

  pgEnum,
  uuid,
  text,
  varchar,
  timestamp,
  boolean,
  uniqueIndex,

  "pending",
  "active",
  "suspended",

    id: uuid("id").defaultRandom().primaryKey(),

# 28. Acceptance Criteria

The database foundation is ready for Phase 1 implementation when:

1.  A user can have multiple authentication identities without duplicate
    accounts.
2.  Roles can be assigned and revoked independently.
3.  One user can hold student and mentor roles.
4.  A mentor profile cannot become publicly discoverable without
    approval.
5.  Verification decisions retain actor, time, reason and history.
6.  Imported profile facts retain source and timestamps.
7.  Consent can be granted and revoked by scope.
8.  Matching runs preserve algorithm version and candidate explanations.
9.  Ineligible mentors cannot be booked.
10. Booking concurrency cannot create overlapping confirmed sessions for
    a mentor.
11. Booking state transitions are auditable.
12. LiveKit secrets and tokens are never stored as public profile data.
13. Session notes have explicit visibility.
14. Messages are accessible only to conversation participants and
    authorized moderation workflows.
15. Mock interview feedback references a versioned rubric.
16. Admin access is permission-checked and audited.
17. Sensitive files are stored privately outside PostgreSQL.
18. Critical events can be published reliably using an outbox or
    equivalent.
19. Deletion and retention policies are implementable.
20. Core Phase 1 workflows do not require an LLM.

# 29. Final Architecture Recommendation

Build MentorMaze as a **modular PostgreSQL-backed application with
strict relational integrity, explicit provenance, and transaction-safe
booking**.

Do not start by creating a large number of microservices or an elaborate
AI data lake. The highest-risk data problems are identity linking,
consent, mentor approval, booking concurrency, session privacy, and
clear ownership of ecosystem data.

The first production schema should prioritize:

1.  Users, identities, roles and permissions.
2.  Student and mentor profiles.
3.  Mentor applications and verification.
4.  Consent, integrations and source provenance.
5.  Skills, goals and matching.
6.  Availability and bookings.
7.  Sessions, notes and action items.
8.  Human mock interviews and rubric reports.
9.  Messaging, notifications, audit and outbox.

This gives MentorMaze a reliable human mentorship foundation and
preserves a clean path to Phase 2 AI mentorship.
